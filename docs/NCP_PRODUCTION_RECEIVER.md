# NCP production first-install receiver

Current placement is existing **GCP test + central Admin/observability**, and a
separate new **NCP production-only** host. NCP admits User/Agent/Hub/YOLO plus the
existing production dependency allowlist. No NCP Admin, learning host, four-server
split, existing GCP bootstrap, public DB/exporter port, or data reset is enabled.

This implementation has four explicit phases. It does not yet activate serving.
Local unit tests use generated files and an injected backend; live Docker/PG,
new NCP installation, migrations, timer/backup restore and production readiness
must have separate exact-source acceptance evidence before rollout.

| Phase | Actual permitted work | Result |
|---|---|---|
| `verify` | Root-owned enrollment, LUKS host, staged artifacts/cache, exact source checkout, six-image release and User bootstrap CI approval checks; no writes | `RECEIVER_INPUTS_VERIFIED` |
| `prepare` | On a new empty host only: durable attempt/proof; isolated network; new private PG data path/container; new `map_prod` from `template0`; independent database marker | `BOOTSTRAP_REQUIRED` |
| separate User controller | One use of existing prepare SQL/plain main/finalize SQL, private independent runtime/migrator roles, login/catalog checks and receipt | `PASS` bootstrap receipt |
| `accept-bootstrap` | Verify exact request identity, finalized receipt, unchanged PG mount/network/container | `BOOTSTRAP_ACCEPTED` |
| `migrate-user` | Existing normal User migrator `migrate` then `validate`, in its isolated disposable job | `USER_NORMAL_MIGRATIONS_COMPLETE` |

All results retain `public_serving=HOLD`. A successful phase is not production
readiness or launch approval. Normal Hub/Agent role/schema provisioning and
migrations, Redis/OSRM and four-app creation, target management/metrics transport,
backup identity enrollment/real recovery, production-specific private readiness,
rollback evidence and a public admission guard remain later gates. The GCP
six-app receiver/watchdog is unchanged. Public edge/proxy/user/yolo must retain
`restart=no` in that later implementation.

## Fixed inputs and trust boundary

Install the reviewed clean Infra Git checkout at `/opt/map-service-infra`, owned
by root with no group/other write access to any source or ancestor. Its HEAD must
match the six-image release `infra_sha` and approved receiver source commit.
The receiver's file SHA must match the staged artifact descriptor. Stage/cache
the approved production artifact bundle with the existing bootstrap tools first.
No image pull, build, cloud create, DNS, Terraform, Git mutation or GCP query is
performed by these phases.

Fill `deploy/ncp-bootstrap/production-runtime.template.json` and install it as
root0600 `/srv/map-prod/secrets/production-runtime.json`. Placeholder values are
rejected. Enrollment uses its canonical JSON SHA256. Approval/release files use
their raw file SHA256. Runtime/request/proof/receipt bindings use SHA256 of UTF-8
JSON with sorted keys and compact `(',', ':')` separators; do not interchange
raw file and canonical hashes.

The release-specific private installation directory is
`/srv/map-prod/installations/<release_name>` and contains:

- `cache-receipt.json` generated by the existing artifact cache;
- the original **six-image** `release.json`, whose four production entries must
  exactly match the artifact image digest and source commit;
- `bootstrap-approval.json`, a separately reviewed wrapper over the exact User
  source CI artifact, with the following closed schema.

```json
{
  "schema_version": 1,
  "status": "approved",
  "source_sha": "EXACT_USER_SOURCE_SHA",
  "github_run_id": "EXACT_SUCCESSFUL_RUN_ID",
  "artifact_sha256": "EXACT_USER_BOOTSTRAP_POSTGRES_VERIFICATION_ARTIFACT_SHA256",
  "bootstrap_postgres_verified": true,
  "reviewer": "IDENTIFIED_REVIEWER"
}
```

An operator must verify run ownership, exact source, CI result and artifact
digest through the release evidence process before pinning this wrapper. The
wrapper and file checks do not independently authenticate GitHub or establish a
real NCP PASS. Artifact security approval is for staging, not serving.

Before `prepare`, provision five independently generated 32-byte lowercase-hex
values as separate root0600, single-link regular files under
`/srv/map-prod/secrets`: `POSTGRES_PASSWORD`, `USER_BOOTSTRAP_MARKER`,
`USER_BOOTSTRAP_PASSWORD`, `USER_DATABASE_PASSWORD`, `USER_MIGRATION_PASSWORD`.
Optional trailing LF is accepted. No value may be reused. The marker is a target
guard, not a substitute for the host/network/DB identity checks. Do not place any
of these values in a command argument, transcript, shared environment or evidence.

`prepare` requires no existing Docker containers or volumes, no prior bootstrap
network and no `/srv/map-prod/data/postgres` path. Images may already be cached.
PG data stays on the verified `/srv/map-prod` LUKS2 mount, using a bind mount; no
Docker named data volume is created on an unverified OS disk. The pinned PostGIS
image starts with `POSTGRES_DB=postgres`; its image initialization never runs on
`map_prod`. Only after PG startup does the receiver create `map_prod` from
`template0` and mark it, before User service schemas/PostGIS/default ACLs/exporters.

## Receiver to User controller contract

`identity_request()` and `verify_bootstrap_receipt()` in
`scripts/ncp-production-receiver.py` define the exact schemas. The receiver
writes root0600 `/srv/map-prod/deploy/bootstrap-request.json` after DB preparation.
Its fields are:

```text
schema_version=1, environment=prod, project=map-prod, database=map_prod
enrollment_sha256, security_approval_sha256, release_manifest_sha256
runtime_contract_sha256, new_host_proof_sha256, marker_sha256, created_at(UTC)
user = {image (immutable digest ref), image_id, source_sha}
postgres = {container_id, image_id, data_path=/srv/map-prod/data/postgres,
            data_uuid (enrolled filesystem UUID), operator=postgres,
            network=map-prod-user-migration}
secret_paths = {each of the exact five secret names above: fixed absolute path}
```

The private `new-host-proof.json` binds the empty host observation, machine and
instance IDs, data UUID, runtime/enrollment hashes and marker hash before any PG
creation. The controller independently rechecks the request, proof, current
host/artifact/source/PG identity and actual pristine DB/catalog/marker before any
DDL. The private PostgreSQL network is internal bridge, IPv6 disabled, isolated
host gateway, with only the exact PG endpoint outside the bounded bootstrap job.
The later serving network is `map-prod-net`; it is not connected by these phases.

The separate User controller writes root0600 `bootstrap-receipt.json` with exactly:

```text
schema_version=1, status=PASS, input_request_sha256
identities = exact request values for:
  environment, project, database, enrollment_sha256, security_approval_sha256,
  release_manifest_sha256, runtime_contract_sha256, new_host_proof_sha256,
  user, postgres, marker_sha256
migrations_executed=4
finalization_complete=true, bootstrap_login_disabled=true
bootstrap_sessions_zero=true, runtime_and_migrator_roles_ready=true
postgres_identity_preserved=true, started_at(UTC), completed_at(UTC)
```

The runtime/migrator-ready flag requires private independent login provisioning,
actual password authentication, and final privilege catalog checks after the
unchanged finalization SQL. It must not be inferred from a zero Java exit or
NOLOGIN alone. The process deadline is120s. On failure or uncertainty, stop only
the exact bootstrap job, quarantine only the independently checked new target
according to User's existing quarantine contract and preserve partial history.
No automatic retry, marker reset, alternate target, database drop or volume
cleanup is exposed. Record only fixed codes/identity hashes, never raw SQL/logs.

The controller additionally writes root0600
`/srv/map-prod/secrets/user-migration.env` with exactly:

```text
USER_MIGRATION_URL=jdbc:postgresql://postgres:5432/map_prod?currentSchema=user_service
USER_MIGRATION_USERNAME=map_user_migrator
USER_MIGRATION_PASSWORD=<private independent migrator value>
```

These credentials are never placed in a serving container. The one-use
bootstrap password must be retired after confirmed finalization and its job
cleanup; the marker and nonsecret receipts remain for diagnosis.

Each independent CLI owns the same root0600
`/srv/map-prod/deploy/deploy.lock` using nonblocking exclusive flock. Invocation
is sequential: receiver prepare exits and releases the lock; User controller
acquires/releases it; receiver accepts and migrates. No parent-held nested lock,
second deployment writer, GCP lock, or reliance on the central Admin is permitted.

## Operator sequence and failure handling

On the reviewed new NCP host only, after exact input/source evidence is complete:

```text
python3 -B /opt/map-service-infra/scripts/ncp-production-receiver.py verify
python3 -B /opt/map-service-infra/scripts/ncp-production-receiver.py prepare
# Run the separately reviewed/pinned User bootstrap controller once.
python3 -B /opt/map-service-infra/scripts/ncp-production-receiver.py accept-bootstrap
python3 -B /opt/map-service-infra/scripts/ncp-production-receiver.py migrate-user
```

`first-install-attempt.json` is written as HOLD before any Docker creation and is
never reused. A lost create/start response retains that marker, any exact known
container identity and the newly created data for explicit quarantine/review.
The receiver neither stops unrelated containers nor deletes anything. The normal
User migration phase also records an attempt before it can mutate the DB.

For later Hub/Agent normal migration, `service-migration-job.py` accepts
`map-prod` only with a closed `x-map-production` pin:

```json
{"environment":"prod","database":"map_prod",
 "postgres_container_id":"EXACT_64_HEX_ID","postgres_image_id":"sha256:EXACT_64_HEX_ID"}
```

The service's runtime DSN, migrator DSN/role and DB must agree with that pin.
The PostgreSQL container/image and production project/service labels are checked
before network creation/attachment. Direct production CLI use additionally
requires scratch `/srv/map-prod/deploy/migrations`, receipt parent
`/srv/map-prod/deploy/receipts`, and `/srv/map-prod/secrets/<service>-migration.env`;
it acquires the shared deploy lock before its service lock. Existing GCP
`map-test`/legacy `map-service` behavior is retained and rejects production pins.
